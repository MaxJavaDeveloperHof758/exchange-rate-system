# Feature Specification: Exchange Rate Management System

**Feature Branch**: `001-exchange-rate-management`

**Created**: 2026-08-21

**Status**: Draft

**Input**: User description: "Exchange Rate Management System — full scope of the company's Full-Stack Technical Assessment brief: daily scheduled ingestion of rates from Fixer.io, a spread-adjusted exchange-rate calculator API, a usage-analytics API, an AI-generated trend-insight API backed by a local LLM, and an Angular frontend with three views (Calculator, Historical Rates & Trend Chart, Usage Analytics Dashboard), all documented via OpenAPI/Swagger."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Get a spread-adjusted rate for a currency pair (Priority: P1)

An internal staff member picks a source currency and a target currency, optionally a specific
past date, and gets back the spread-adjusted exchange rate for that pair, computed from rate data
the system already holds locally.

**Why this priority**: This is the core value proposition of the whole system — everything else
(trends, analytics) is built on top of this single lookup capability. Without it, there is no
product, and it is independently deployable and demoable on its own.

**Independent Test**: With rate data pre-loaded for at least two currencies, submit a lookup for
a known pair and date and verify the returned rate matches the expected spread-adjusted
calculation; submit a lookup for a date with no stored data and verify a clear "not available"
outcome rather than a wrong or blank number.

**Acceptance Scenarios**:

1. **Given** stored rates for EUR (rate-to-USD 0.8, spread 1%) and PLN (rate-to-USD 3.7, spread
   4%) on 2024-03-15, **When** a user requests the EUR→PLN rate for 2024-03-15, **Then** the
   system returns 4.44 (the higher of the two spreads, 4%, applied) and records that the query
   happened.
2. **Given** no date is specified, **When** a user requests a currency pair's rate, **Then** the
   system returns the rate computed from the most recent date for which both currencies have
   stored data.
3. **Given** a user requests a currency pair for a date with no stored rate data, **When** the
   lookup runs, **Then** the system clearly reports that no rate is available for that date
   (a distinct, specific error) rather than returning an empty, zero, or misleading value.
4. **Given** a user requests a rate using the same currency on both sides of the pair (e.g.
   EUR→EUR), **When** the lookup runs, **Then** the system returns a rate of 1 with no spread
   applied, rather than an error or a nonsensical calculated value.
5. **Given** a user requests a rate using an unrecognized or misspelled currency code, **When**
   the lookup runs, **Then** the system rejects the request with a clear, specific error
   distinguishable from a "no data for this date" error.
6. **Given** a successful lookup just occurred, **When** the same or a different user repeats it,
   **Then** the recorded usage count for each of the two currencies involved increases by exactly
   one per successful lookup, even when many lookups happen at the same time.

### User Story 2 - Review a historical rate trend with an AI-generated insight (Priority: P2)

An internal staff member picks a currency pair and a date range and sees the raw historical rates
for that period (as a table) alongside a visual trend (a chart), plus a short, plain-language
summary of what happened over that period, generated by an AI model that has actually looked at
that specific data.

**Why this priority**: This is the differentiating, harder-to-build capability that turns raw
numbers into something a non-technical reviewer of the dashboard can act on at a glance; it
depends on User Story 1's underlying rate data existing, but is independently demonstrable once
that data is present, without requiring User Story 1's endpoint to be called first in the same
session.

**Independent Test**: With at least two weeks of stored rates for a pair, select that pair and a
date range covering the stored data; verify the table lists the correct raw rates, the chart
visibly reflects the same movement, and the generated insight text references a
direction/magnitude consistent with the actual data (and changes if a different date range with
different data is selected).

**Acceptance Scenarios**:

1. **Given** two weeks of stored rates for a currency pair showing a clear upward move, **When**
   a user selects that pair and date range, **Then** the table and chart both show the upward
   move, and the AI insight text describes an increase (not a generic or unrelated statement).
2. **Given** the user changes the date range to a period with materially different data, **When**
   the view refreshes, **Then** the AI insight text changes to reflect the new period's actual
   movement.
3. **Given** the AI insight is being generated, **When** the user is viewing the chart, **Then**
   the interface shows a clear loading indicator for the insight until it arrives, without
   blocking the table or chart from displaying.
4. **Given** the AI model is temporarily unavailable, **When** the insight is requested, **Then**
   the user sees a clear message that the insight could not be generated, while the table and
   chart still display normally.
5. **Given** a selected historical date range where only part of the range has stored data,
   **When** the view loads, **Then** the table/chart show what is available and clearly indicate
   which parts of the requested range are missing, rather than failing the whole request or
   fabricating missing points.
6. **Given** a selected date range spanning a single day, **When** the insight is generated,
   **Then** the commentary describes a single-day observation rather than misrepresenting it as a
   multi-day trend; **given** a selected date range spanning multiple years, **When** the insight
   is generated, **Then** the commentary still produces a coherent, readable summary rather than
   an overloaded or truncated response.

### User Story 3 - View usage analytics across currencies (Priority: P3)

An internal staff member (e.g., a manager) views a dashboard showing which currencies are looked
up most often and over what time periods, to understand usage patterns across the organization.

**Why this priority**: Valuable for understanding adoption and usage patterns, but it is purely
an observability layer on top of data generated by User Stories 1 and 2 — it delivers no value on
its own until lookups have actually happened, so it is correctly built last.

**Independent Test**: After performing a known number of lookups involving specific currencies,
open the analytics view and verify the displayed counts and recency match the lookups actually
performed.

**Acceptance Scenarios**:

1. **Given** a currency has been involved in a known number of successful lookups, **When** the
   analytics view is opened, **Then** that currency's displayed usage count matches the known
   number.
2. **Given** multiple currencies have been queried with different frequencies, **When** the
   analytics view is opened, **Then** the most-queried currencies are visibly distinguishable from
   the least-queried ones.
3. **Given** no lookups have ever been performed for a given currency, **When** the analytics
   view is opened, **Then** that currency either does not appear or is clearly shown with zero
   usage — never with missing/undefined data.

---

### Edge Cases

- What happens when a user requests a rate for the same currency on both sides of the pair (e.g.,
  EUR→EUR)? The system must return a sensible result (rate of 1, no spread) rather than an error
  or a nonsensical calculated value. *(Covered by User Story 1, Acceptance Scenario 4.)*
- What happens when the daily ingestion job runs more than once for the same day (e.g., a manual
  retry, or two service instances both firing at 00:05 GMT)? Stored data for that currency and
  date must end up correct and singular — no duplicate rows, no inconsistent values from a
  partial double-write.
- What happens when the upstream rate provider (Fixer.io) is unreachable or returns an error at
  fetch time? The system must not lose previously stored data, and must make the failure visible
  (e.g., in logs/monitoring) rather than silently leaving the day's data missing with no trace.
- What happens when a user requests an unsupported or misspelled currency code? The system must
  reject it with a clear, specific error rather than treating it as a valid zero/blank rate.
  *(Covered by User Story 1, Acceptance Scenario 5.)*
- What happens when a user selects a historical date range where only part of the range has
  stored data? The table/chart must show what is available and make clear which parts of the
  requested range are missing, rather than failing the whole request or fabricating missing
  points. *(Covered by User Story 2, Acceptance Scenario 5.)*
- What happens when the historical date range selected is very large (e.g., years) or has only a
  single day? The trend view and AI insight must still behave sensibly. *(Covered by User Story
  2, Acceptance Scenario 6.)*
- What happens when many users perform lookups at the exact same moment? Usage counters must not
  lose or duplicate increments under that concurrent load.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST fetch current exchange rate data from an external rate provider
  (Fixer.io) on an automatic daily schedule (once per day, at 12:05 AM GMT), without requiring
  manual intervention.
- **FR-002**: System MUST record, for every stored rate, the date the rate is valid for as
  reported by the external provider — never the date/time the system happened to fetch it.
- **FR-003**: System MUST treat a repeated fetch for a currency and validity date that is already
  stored as an update-in-place, never producing more than one stored record for the same currency
  and validity date.
- **FR-004**: System MUST remain correct (no duplicate or corrupted rate data) even if the daily
  fetch is triggered redundantly, including by more than one running instance of the system at
  the same time.
- **FR-005**: System MUST let a user request the spread-adjusted rate for a source currency and a
  target currency, with an optional specific date.
- **FR-006**: System MUST compute the spread-adjusted rate using only rate data already stored
  locally — a rate lookup MUST NOT depend on reaching the external provider at request time.
- **FR-007**: System MUST apply the spread of whichever of the two currencies in the pair carries
  the higher spread, using the fixed spread reference table defined for this system: base
  currency (as returned by the Fixer.io API key) 0.00%; JPY/HKD/KRW 3.25%; MYR/INR/MXN 4.50%;
  RUB/CNY/ZAR 6.00%; all other currencies 2.75%. The formula is
  `adjustedRate = (toCurrencyRateToUSD / fromCurrencyRateToUSD) × ((100 − MAX(toSpread, fromSpread)) / 100)`.
- **FR-008**: System MUST use the most recent available stored rates for a pair when no date is
  specified in a lookup.
- **FR-009**: System MUST clearly reject, with a specific and distinguishable outcome (an
  appropriate HTTP error), a lookup for a date where rate data for one or both requested
  currencies is not stored.
- **FR-010**: System MUST reject a lookup that names an unsupported or unrecognized currency code
  with a specific and distinguishable outcome, separate from the "no data for this date" outcome.
- **FR-011**: System MUST increase a per-currency usage counter for each of the two currencies
  involved in every successful rate lookup, exactly once per successful lookup.
- **FR-012**: System MUST keep usage counters accurate when multiple lookups happen concurrently —
  concurrent successful lookups MUST NOT be lost, double-counted, or corrupt each other.
- **FR-013**: System MUST provide a way to view usage statistics showing, at minimum, the query
  count per currency and the dates on which queries were made.
- **FR-014**: System MUST let a user request historical rate data for a currency pair over a
  selected date range, returning the raw rates that are actually stored for that range.
- **FR-015**: System MUST generate a short, natural-language commentary on the rate trend for a
  selected currency pair and date range, and this commentary MUST be produced by an AI model that
  is given the actual historical rate values for that specific period, not a static or templated
  statement independent of the data.
- **FR-016**: System MUST constrain the AI-generated commentary (via its instructions to the
  model) to a short, relevant, non-generic insight — not generic filler text that would apply
  equally to any dataset.
- **FR-017**: System MUST clearly indicate to the user when the trend commentary is being
  generated (a loading state) and when it could not be generated (an error state), independently
  of whether the raw historical data and chart are available.
- **FR-018**: System MUST expose three user-facing views: a rate Calculator, a Historical Rates &
  Trend Chart (table + line chart + AI insight, side by side), and a Usage Analytics Dashboard.
- **FR-019**: Frontend MUST allow a user to point the application at a different backend location
  without needing a source-code change — a configuration change is sufficient, and the
  application MUST run via a standard local development server pointed at that configured
  backend.
- **FR-020**: Frontend MUST provide input validation and clear, specific error messaging when a
  request to the backend fails or returns invalid input feedback, for both the calculator and the
  historical-trend views.
- **FR-021**: System MUST document every exposed capability (endpoint) in a form that is
  human-browsable (an interactive API documentation page), so that a reviewer can discover and
  try each capability without reading source code.
- **FR-022**: System MAY provide a way to manually trigger an out-of-schedule rate fetch/update
  without resetting or altering existing usage counters. *(Optional, per the source brief —
  Section 4.4.)*

### Non-Functional Requirements

- **NFR-001 (Numeric Precision)**: All stored and calculated rate, spread, and adjusted-rate
  values MUST be represented and computed with exact decimal precision — floating-point
  representation error MUST NOT be observable in any returned rate value (e.g., a value that
  should be exactly 4.44 MUST NOT be returned as 4.440000000000001 or similar).
- **NFR-002 (Concurrency Correctness)**: Usage counters MUST remain exactly correct under
  concurrent load. Specifically, at least 50 simultaneous successful lookups involving the same
  currency MUST result in that currency's counter increasing by exactly 50 — zero lost and zero
  duplicated increments.
- **NFR-003 (Ingestion Idempotency Under Multi-Instance Deployment)**: The daily ingestion process
  MUST produce identical, correct stored data regardless of whether it is triggered once by a
  single instance or concurrently by multiple running instances of the system — re-ingesting an
  already-ingested day MUST NOT grow the stored row count for that day.
- **NFR-004 (Graceful Degradation — Upstream Provider)**: If the external rate provider is
  unreachable or errors during the scheduled fetch, the system MUST retain all previously stored
  rate data unchanged and MUST make the failure observable (e.g., logged), rather than silently
  leaving that day's data missing with no trace or corrupting existing data.
- **NFR-005 (Graceful Degradation — AI Model)**: If the local AI model is unavailable or fails to
  respond, the trend-insight feature MUST fail in isolation (a clear, distinct error state for the
  insight only) without preventing the historical rate table and chart from loading and
  displaying normally.
- **NFR-006 (No Request-Time External Dependency)**: Rate lookups (Calculator and Historical
  views) MUST be servable entirely from locally stored data, with no synchronous call to the
  external rate provider at request time, so that lookup availability and latency do not depend
  on that provider's uptime.
- **NFR-007 (Local Runnability)**: A reviewer MUST be able to run the complete system (backend,
  scheduled ingestion, AI insight, and frontend) locally using only documented setup steps, with
  zero source-code edits required beyond configuration (e.g., environment variables, a local
  model pull).
- **NFR-008 (Trust Boundary — Security)**: This is an internal tool operated on a trusted network
  for internal staff; user authentication, authorization, and per-user data isolation are
  explicitly out of scope for this feature (see Assumptions) — this MUST NOT be treated as an
  accidental omission but as a stated boundary.
- **NFR-009 (Responsiveness)**: Since rate lookups and historical queries are served from local
  data only (NFR-006), they MUST feel immediate to a user (near-instant, no perceptible
  provider-roundtrip delay); only the AI-insight generation is expected to have a
  user-perceptible wait, which MUST be covered by the loading state in FR-017.

### Key Entities

- **Exchange Rate Record**: A stored rate for one currency on one specific validity date —
  includes the currency code, its rate relative to the reference currency, and the date the rate
  is valid for (as reported by the provider, not the fetch time). Unique per (currency, validity
  date).
- **Currency Spread**: A property derived from a fixed reference table (not stored per-fetch) that
  maps a currency code to a spread percentage, used only during the rate-calculation step.
- **Currency Usage Counter**: A running count of how many successful pair lookups a given currency
  has participated in (as either side of the pair), plus the most recent date it was queried.
- **Trend Insight**: An ephemeral, AI-generated natural-language summary tied to a specific
  currency pair and date range and the historical rate values within it; not necessarily
  persisted long-term.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A user can obtain a spread-adjusted rate for any two currencies with locally
  available data in a single request, with the result matching the fixed formula's expected
  output for known test inputs (e.g., the EUR/PLN worked example yields 4.44).
- **SC-002**: 100% of lookups for a date with no stored rate data receive a distinct, clear
  "unavailable" outcome rather than a fabricated or zero value — verified across at least the
  edge cases identified above.
- **SC-003**: After any number of concurrent successful lookups (tested at a minimum of 50
  concurrent requests), the recorded usage counts for each involved currency exactly equal the
  number of successful lookups that involved that currency — zero lost or duplicated increments.
- **SC-004**: Re-running the daily ingestion process for a day that was already ingested results
  in exactly one stored record per currency for that day, with no growth in stored row count.
- **SC-005**: A user reviewing a historical trend for a period with a clear directional move
  receives an AI-generated insight whose described direction (e.g., "rose", "fell", "stable")
  matches the actual direction of the underlying stored data at least 9 times out of 10 test
  periods.
- **SC-006**: A user can view usage analytics and correctly identify, within 10 seconds of
  opening the view, which currency has been looked up the most.
- **SC-007**: A reviewer can run the full system locally (backend, scheduled job, AI insight, and
  frontend) using only the documented setup steps, and successfully complete a rate lookup, a
  historical-trend view, and an analytics view — with zero source-code edits required beyond
  configuration.
- **SC-008**: Every exposed system capability is discoverable and directly triable from the
  interactive API documentation page without reading any source code.

## Assumptions

- The external rate provider (Fixer.io free tier) is queried at most once per day by the
  scheduled ingestion process; on-demand/ad-hoc provider calls at lookup time are out of scope by
  design (per the brief, lookups must be servable from locally stored data alone).
- This is an internal tool used on a trusted network; user authentication, authorization, and
  per-user data isolation are out of scope for this feature (see NFR-008).
- Historical rate data is read-only once ingested through the normal daily process — there is no
  requirement for a user-facing capability to manually edit or delete individual stored rate
  records.
- The AI-generated trend insight is a best-effort, qualitative commentary; it is not expected to
  be financially precise, and its unavailability (e.g., local model not running) must degrade the
  experience gracefully rather than block the rest of the historical-trend view.
- "Usage" for analytics purposes is defined at the currency level (a lookup increments both the
  source and target currency's counters), not at the ordered-pair level, matching the response
  shape suggested by the source brief.
- A single, unauthenticated frontend is sufficient — there is one shared view of the data and
  analytics, not per-user personalization.
- Multi-instance safety for the daily ingestion job needs to prevent duplicate/corrupted data, not
  necessarily prevent the provider from being called more than once on a given day by different
  instances — correctness of stored data is the hard requirement; provider call efficiency is a
  secondary concern.
